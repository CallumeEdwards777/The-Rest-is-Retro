Part 1

The big picture: three machines

The whole site is three programs talking to each other. Every feature below is just a different conversation between them.

THE FACE

React app

Everything you see and click. Runs in the browser at localhost:5173. It holds no real data; it asks for it.

THE RULES

Express API

A program at localhost:3001 that answers requests: "give me the items", "buy this", "save that". It enforces every rule: who owns what, what can be bought, who you are.

THE MEMORY

MySQL database

Where everything lives when the tab closes: users, the 48 items, saved hearts. Named vintage_db. Only the API talks to it, never the browser.

browser ⇄ asks the API ⇄ reads and writes the database

One real example: you press Buy now. React sends "buy item 2" plus your identity token to the API. The API checks the item exists, is verified, isn't yours, isn't sold, then writes "sold" into the database and answers with an order reference. React takes you to the confirmation screen. Total time: a blink.

Part 2 · learn these five

Saying it out loud

Five true sentences for the presentation, each backed by something on this page.

The pitch. "Here you buy items that made a dent in history. Every listing leads with its story, and you browse by decade, not by keyword. eBay and Depop authenticate sneakers and handbags, because that's where the money is; nobody does it for a Walkman or a lava lamp, where the buyer's real questions are 'is this really from 1979, and does it still work?'. We answer both: evidence-based verification and honest condition labels."
The shape. "It's a classic three-part app: a React front end, an Express API that enforces every rule, and a MySQL database. The browser never touches the database directly."
The trust story. "We stayed honest about being C2C: the Verified badge means the buyer is covered by evidence checks, not that we handled the item. The server enforces it: pending items literally cannot be bought. Try it on the Motorola RAZR, the button refuses." (If refunds come up: that's the policy the product needs, stated in the FAQ, not something we coded.)
The personal touch. "First-time visitors answer two questions and the shop rearranges around them, like a mobile app onboarding. The answers are saved on the account, so they follow you across devices."
The build. "We rebuilt from a half-migrated template: repaired the client-server contract, designed the brand as a token system, then shipped buying, selling, photo uploads, hearts and onboarding, each verified in a real browser before commit. Eighty commits."

Before you go on stage:

Log out and back in first. Login notes expire after two hours, but the header keeps showing your initials. Stale note plus Buy now equals a red error mid-demo. A fresh login resets the clock.
Demo the cross-device trick with an account you create live in the quiz. The three seeded users have no saved preferences, so logging in as vintage_vera on a second browser personalises nothing. A quiz-born account proves it perfectly.
Don't buy your own listing. If you list an item during the demo, buy something seeded instead: new listings are pending (not buyable) and the API refuses self-purchases anyway.
Part 3

A buyer's journey

This is the demo path, in order. Each step is a feature we built.

  1. First visit: the quiz. A brand-new visitor is redirected to two questions: which decades, which categories, each choice a photo tile.Answers are stored in the browser under the name onboarding. Anyone already logged in on that browser skips this gate. Deep links like /?era=1990s skip it too.
  2. Save your picks. A third panel offers signup or login ("Awesome! Create an account to save your preferences"), with a quiet "just browse" escape.Signing up from inside the quiz also writes the answers onto your account in the database, so they follow you to any device.
  3. A shop that's already yours. The browse page opens with your decades and categories pre-selected and the headline switches to "Your favourites, back on sale."The filter chips are real buttons: everything stays adjustable.
  4. Finding things. Search in the header (searches everything, ignoring your filters on purpose), decade and category chips with live counts, and decade links in the footer that deep-link the shop.
  5. The item page. Big photo on an amber plate, price, condition label, the seller (clickable, goes to their shop), the TRR guarantee box, the story, the facts, and three more finds from the same decade."The story" is each item's own history in its seller's words: it's what makes a listing here feel like an artefact, not an ad.
  6. Buying. Buy now works only on verified items; pending ones say so and refuse. Two people can't buy the same thing: the database flips it to sold exactly once.You land on a confirmation with an order reference like TRR-ORD-0002, and back on the grid the item now wears a Sold badge.
  7. Hearts. The ♡ on every card saves an item to your account; the Saved page collects them. Logged out? A tap sends you to login first.
Part 4

A seller's journey

  1. List an item. Title, story, price, decade, category, condition, and a photo (checked to be an image type, capped at 5MB).The photo is stored by the API in an uploads folder; the listing points at it.
  2. Pending verification. Every new listing starts here. It can be browsed and hearted, but not bought. Sellers cannot award themselves the Verified badge: the server decides status, never the form.
  3. My listings. Your items with status pills: Verified, Pending, Sold. Edit and Delete exist only for the owner: the server checks that the person asking is the seller before touching anything.
  4. Sold, and back again. When something sells it flips to Sold everywhere. A Relist button puts it back to pending, so a stray demo purchase is a one-click recovery.
Part 5

Feature by feature, under the hood

Each card: what you see, then what actually happens. File names are where the code lives, in case anyone asks.

GlueAccounts and staying logged in

You sign up or log in once; the site remembers you across refreshes, and greets you with your initials in the header.

Passwords go through bcrypt before they touch the database: password123 is stored as a 60-character scramble starting $2b$10$, and there is no way back from it. The 10 is a deliberate slowness setting: each check costs a fraction of a second, unnoticeable at login, ruinous for someone guessing millions. Login never compares passwords; it rehashes what you typed and compares scrambles. On success the API hands back a token: a note saying "this is user 1, expires in two hours", carrying a signature the server can check and nobody can forge. The note is readable, not secret, so it holds an id and never a password. Usernames and emails are unique, so login accepts either. Files: server/routes/user.js, server/models/user.js.

BuyThe welcome quiz and the personalised shop

Two photo-tile questions, an account nudge, then a shop pre-filtered to your taste.

Answers live in the browser (localStorage) and, if you sign up or log in from inside the quiz, also on your user row in the database, in a preferences column. On any later login they're pulled back down, which is why a wiped browser still knows your decades. The browse page reads them as its starting filter. Files: client/src/components/Welcome.jsx, client/src/onboarding.js.

BuySearch, chips and decade deep links

Type "walkman", press enter, get the Walkman, whatever filters were on. Chips narrow by decade and category with live counts. Footer decade links open the shop already filtered.

Search asks the API to look through titles and descriptions in the database (GET /api/items/search). The chips filter in the browser: all 48 items are already loaded, so filtering is instant. A link like /?era=1980s is read from the address bar and applied as the filter. Files: client/src/components/ItemList.jsx, server/routes/item.js.

TrustThe Verified badge and the TRR guarantee

Verified items carry a teal tick and a guarantee box: evidence checked, full refund if it's not genuine.

This is the shop's honest C2C story: we never touch the items. Sellers submit label, barcode or serial evidence; it's checked before the listing goes live; the badge means "you're covered", not "we inspected it in a studio". In code, it's a status field the server controls: new listings are always pending, and only verified ones can be bought, enforced at the API so no clever browser can bypass it. Files: server/routes/item.js, FAQ copy in client/src/components/Faq.jsx.

TrustCondition labels

Every item states its condition: Tested & working, Display only, or Wear consistent with age.

One extra column on the item table. The API keeps the label only if it is one of the three known values and silently drops anything else, so a hand-crafted request can't invent a condition (the check lives in server/routes/item.js, on both create and edit). The 48 seeded items were labelled by reading each description: only genuinely untestable things got Display only, and there are exactly four (an untested Sega Genesis, mint boxed Beanie Babies, a sealed Tamagotchi, a boxed Bratz set). Sellers pick a label when listing; editing without picking changes nothing. Files: server/routes/item.js, client/src/components/ItemForm.jsx.

BuyBuying, exactly once

Buy now gives you a confirmation and an order reference; the item shows Sold everywhere immediately.

The API refuses to sell what is unverified, already sold, or your own listing. The flip itself works like the last seat on a flight: two people click in the same second, both requests reach the database, and the write says "mark this sold only if it is still verified". The first request changes one row; the second changes zero rows, and zero is how the API knows to answer with a polite no. One conditional write is the entire defence against selling the same Walkman twice. There's no payment: money is out of scope, the order reference stands in for it. Files: server/routes/item.js, client/src/components/Confirm.jsx.

BuyHearts and the Saved page

Tap ♡ anywhere, it fills; the Saved page collects your finds; unsaving removes them live.

A tiny table in the database pairs your user id with an item id, one row per heart. Three API endpoints: list mine, save one, unsave one, all requiring your token, all scoped to you (no way to read anyone else's). The browser keeps the list in shared memory so every heart on every page agrees, updates optimistically, and double-taps can't race. Files: server/routes/savedItem.js, client/src/contexts/SavedContext.jsx.

SellListing with a photo

Fill the form, attach a photo, done: your item appears with its picture.

The photo travels to the API, which accepts only image types, caps the size at 5MB, renames the file randomly, and derives the extension from the declared type rather than the filename, which blocks the easy trick of naming a web page "photo.png". Honest limit: the API trusts the type the browser declares rather than reading the file's actual bytes; byte-checking is on the next-steps list. The 48 seeded items use pre-shot photos matched by item code. Files: server/utils/upload.js, client/src/components/ItemForm.jsx.

SellOwnership: edit, delete, relist

You can manage your listings; you can't touch anyone else's, and they can't touch yours.

Every changing request carries your token; the API compares the item's seller_id with the id inside the token and answers 403 if they differ. Relist is the same check plus one rule: only sold items go back to pending. Files: server/routes/item.js, client/src/components/MyListings.jsx.

SellSeller shops

Tap a seller's name on any item and you get their whole shop: "16 relics listed".

The page asks the API who the seller is (id and username only: emails are never exposed to logged-out visitors) and filters the item list to theirs. Files: client/src/components/SellerPage.jsx, server/routes/user.js.

GlueThe design system

Cream paper, burnt orange and teal, chunky serif headlines, a sunburst hero, cards that print an ink block when you hover.

One palette (cream, ink, orange, amber, teal) and two typefaces (Fraunces for display, Inter for text) defined once as variables in a single stylesheet; every screen reuses them, which is why everything matches, this page included. The hero's sunburst and grain are pure CSS, no images. Decade badges are colour-coded: orange '70s, amber '80s, teal '90s, ink Y2K. File: client/src/index.css, decisions in markdowns/DESIGN.md.

GlueDemo data and the reset button

The shop always has 48 believable items across 4 decades and 5 categories, with three ready-made users.

npm run seed drops every table and rebuilds them in dependency order: 5 categories, then 3 users, then 48 items, because an item can't point at a seller who doesn't exist yet. Users are created one at a time on purpose: creating them in a batch races the password scrambler and shuffles their ids, which would silently hand every item to the wrong seller. Same 48 items, same photos, same three users (vintage_vera, disco_dan, y2k_yasmin, password password123) every run: a five-second undo for the whole world. Files: server/seeds/.

Part 6

Six tech words, translated

API

A program you talk to with requests instead of clicks. Ours answers at localhost:3001 and every answer is data, not pages.

Endpoint

One address on the API for one job. POST /api/items/2/buy means "buy item 2". The site uses two dozen.

Token (JWT)

A tamper-proof note the API signs at login: "this is user 1, for 2 hours". Sent with every request that needs to know who's asking. Readable but unforgeable, so it never carries a password.

localStorage

A small notebook inside your browser. We keep the token, your session name, and your quiz answers there so refreshing doesn't forget you.

Component

A reusable piece of screen. The item card is one component drawn on four screens (browse, item page, Saved, seller shops), and two more screens borrow its price and photo helpers.

Seed

A script that fills an empty database with known starting data. Ours plants the 48 relics and 3 users, identically every run.

Part 7 · the defence layer

If they ask the hard question

Nine questions a sharp marker might ask, with the honest answers. Knowing the limits is what makes the rest credible.

"Who moves an item from pending to verified?"

Nobody can, yet: verification is a staff action and this build has no staff role. The server creates every listing as pending, and only a reseed promotes anything. That was a deliberate cut: an admin role means a second user type, a queue screen and an audit trail, a bigger feature than buying itself. What we did build is the half that protects the buyer: the API refuses to sell a pending item no matter what the browser sends. The admin queue is first on the next-steps list.

"I just bought something. Where's the order? Does the seller know?"

The sale is recorded as one fact: the item's status becomes sold, which is what stops anyone else buying it. There is no orders table, no buyer stored, and no email: the confirmation screen's "seller has been notified" shows what the product would do, not what the code does. The order reference is honestly just the item's own id dressed up. The first table I'd add tomorrow is orders: buyer, item, price paid, timestamp. That one table also buys order history and makes the reference real.

"What breaks at 50,000 items?"

Loading everything. At 48 items, fetching the whole catalogue makes filtering instant, a feature. At fifty thousand it's the bug: browse, the item page, My Listings and seller shops each pull the full list, and search scans every row. The fixes are all standard and all server-side: paginate the list, move decade and category filters into the database query, add a per-seller query, and give search a proper text index.

"What's the weakest part of the design?"

Three things, in honesty order. Trust is asserted, not administered: there's no one to do the verifying. A sale leaves no record beyond a flag. And server-side validation is thin: required fields are checked, but nothing stops a negative price. All three are top of the next-steps list, and none of them undermine what is enforced: ownership, uniqueness, the buy rules.

"What stops someone stealing the login token?"

On localhost, nothing needs to. In production three things would change: the token would move from localStorage into a cookie scripts can't read, login would get rate limiting so passwords can't be guessed at network speed, and the server would refuse to start without its signing secret instead of falling back to a development one. Naming these is the point: the token design is standard, the hardening is deployment work we haven't needed yet.

"Why MySQL?"

The data is rows all the way down: every item has the same fields, belongs to exactly one seller and one category, and a heart is nothing but a pair of ids. That's a relational shape. Buying also leans on the one thing relational databases are great at: a single conditional write that only lands if the row is still verified, which is what makes double-selling impossible. And it's the stack the whole team can read.

"What would you build next?"

In order: the admin verification queue (unblocks the whole trust story), an orders table, server-side paging and filtering, real byte-level image checking, and automated tests around the buy route, because two users colliding there is the one thing clicking can't test. Then the fun one: Retro Curators, taste-maker shelves in the spirit of Steam Curators.

"Any automated tests?"

No. We verified in a real browser, screenshotting each state before each commit, and the API's rules were exercised with direct requests. If I added tests I'd start with the buy route: the race between two simultaneous buyers is the one behaviour a human can't check by hand.

"Is it live?"

Local only, by choice: presenting from localhost removes a whole category of demo risk. It's deployment-shaped though: the client reads its API address from one environment variable, so going live is a host for the API, a managed MySQL, and one seed run.
